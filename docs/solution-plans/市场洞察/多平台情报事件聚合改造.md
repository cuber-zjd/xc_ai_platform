# 多平台情报事件聚合改造

## 一、问题

百度资讯、博查、豆包联网搜索和站点适配器可能返回同一事件的不同转载链接。只按 URL 去重会让同一件事生成多条正式情报，继而重复进入向量库、知识图谱和报告素材，影响用户阅读和报告结论权重。

## 二、处理口径

系统采用“一个事件、一条正式情报、多个报道来源”的结构：

- `insight_intelligence` 是事件主体，承载标题、摘要、业务价值、分类、标签和权限。
- `insight_intelligence_source` 是报道来源，一条事件可关联百度、博查、豆包和具体网站的多篇报道。
- 情报中心、首页、RAG、知识图谱和报告素材只按事件主体计数。
- 多来源用于交叉印证和原文追溯，不重复放大同一信号。

## 三、自动归并流程

1. 搜索阶段先做 URL 去重，拦截相同链接。
2. 候选进入完整 AI 评审前，检索同一业务对象最近 10 天的正式情报。
3. 依次比较归一标题、标题相似度、摘要相似度和事件动作是否相容。
4. 确定性规则无法判断但相似度较高时，调用现有情报资产向量做语义复核。
5. 命中同一事件后，将新报道追加为来源，候选标记为已转正式并指向既有事件，不再进行完整 AI 评审。
6. 更新既有资产的来源信息，正式情报数量、向量和图谱节点均不增加。

事件动作分为新品、扩产、价格、融资并购、合作、政策、风险、技术和人事等组。标题相似但动作冲突的内容不会自动合并，避免把同一企业的不同经营动作误认为同一事件。

## 四、页面表现

- 单一来源事件仍展示原文入口。
- 多来源事件显示“`N 个来源共同报道`”，标题进入详情页查看全部来源。
- 来源按可信度、发布时间排序，政府、交易所和权威媒体优先。
- 报告和 AI 助手只检索事件主体，同时可以引用多个来源作为交叉证据。

## 五、历史数据处理

2026-07-14 执行历史严格归并：

- 扫描在用正式情报：4,134 条。
- 识别高把握重复组：174 组。
- 合并重复正式情报：198 条。
- 迁移新增来源：111 条。
- 迁移候选关联：275 条。
- 迁移个人收藏：12 条。
- 迁移显式授权：5 条。
- 完成后多来源事件：96 个。

历史脚本为 `backend/scripts/insight_merge_duplicate_events.py`。默认只预演并输出 JSON；显式传入 `--apply` 才会执行。历史清理只处理同一业务对象、标题归一后完全一致、发布时间相距不超过 4 天且事件动作不冲突的记录。

## 六、验证方式

```bash
cd backend
uv run ruff check app/services/agent/insight/event_aggregation_service.py scripts/insight_merge_duplicate_events.py
uv run python scripts/insight_merge_duplicate_events.py --days 365
uv run python scripts/insight_merge_duplicate_events.py --apply --days 365

cd ../frontend
pnpm build
```

后续采集验收重点：同一新闻被多个发现源命中时，正式情报只增加一条，详情中的来源数量增加；资产、向量、图谱和报告素材不应产生重复事件。
