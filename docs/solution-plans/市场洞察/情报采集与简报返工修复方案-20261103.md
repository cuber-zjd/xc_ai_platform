# 情报采集、文章生成、审阅与发布全流程修复方案

日期：2026年11月3日。

状态：用户已确认实施，首批模型升级与已证实的数据损失修复已完成本地代码及定向回归；尚未部署，完整方案并未全部完成。已增量注册通过探针验证的模型，未修改定时任务、报告和推送名单。具体完成项、缺口及验收边界见[首批实施记录](./模型升级与证据链首批修复实施记录-20261103.md)。

阅读说明：一至八节为已验证问题和修复优先级；九至十八节为完整目标流程，重点说明文章如何生成、如何检查、如何审阅发布。拟新增能力不代表系统已经具备。具体阈值、模板和发布政策须业务确认，不在本方案中擅自改变。

依据：[审阅补充资料实测](./审阅补充资料搜索与入库断点实测-20261102.md)、[历史差异总报告](./健源御馨全历史周报月报差异总报告-20261102.md)、[报告返工原因分析](./健源御馨报告返工差异与整改建议-20261102.md)。

## 一、要解决什么

目标不是让情报数量或报告字数无限增加，而是：重要消息找得到、可核验、有用的材料不被无故丢弃、两家公司不串题，审阅组主要调整判断和表达，不再重做资料搜集与事实纠错。

按“搜索发现 → 对象归属 → 正文获取 → 日期核验 → 情报入库 → 报告选材 → 写作核对”逐段修复。先处理已经有直接证据的损失，再扩展覆盖。

## 二、第一阶段：先接住已经找到的资料

### 1. 企业名称能认全，但不能乱认

现状：配置是 `Roquette Frères`，搜索结果只出现 `Roquette`，就可能无法分配给监测对象。

拟改：

- 在既有企业档案和监测配置基础上维护标准名、中文简称、英文简称及已确认别名；匹配时规范大小写、空格、连字符和重音符号。
- 别名与集团、子公司关系分开管理，不把集团全部业务自动归给某一家子公司；短词同名或缩写有歧义时，结合官网域名、地点和上下文判断。
- 一条消息可以关联多个对象。无法可靠归属的保留为待匹配线索，不能静默消失，也不能默认给所有公司开放。
- 权限沿用后端规则；新增对象关联不得意外扩大可见范围。归属不确定的资料暂不进入面向业务用户的自动报告。

验收：罗盖特、宜瑞安、ADM等已发现的匹配失败样本能正确归属；同时增加同名公司、集团与子公司的反例，防止召回提高却串公司。

### 2. 原网页抓不到，继续寻找同事件的可靠来源

现状：富锦央视移动页正文失败，但腾讯上的央视官方账号转载可以读取；多个站点先等Firecrawl约30秒，再转直接HTTP。

拟改：

- 先检查已缓存正文和同事件已有来源，再按网站能力选择直接HTTP或动态渲染；不能所有站点都机械等待一次相同失败。
- 原页失败时，优先使用已经搜到的同事件转载。依据主体、动作、关键数字和时间确认同一事件，不把相似主题文章拼成一篇。
- 正文判定增加文章主体、段落有效性及“正在加载、导航、验证页”等信号，不再仅靠超过200字。
- 记录真实抓取方式与证据级别，中文研究介绍不能标成已经读取论文全文。
- 先调查Firecrawl的队列、浏览器、目标页加载和服务超时，确认408原因后再调整；目前尚未证明其内部根因。
- 403、429及验证码触发站点熔断，不密集重试或绕过限制；替代来源也须遵守站点预算、SSRF和响应大小约束。

验收：富锦样本能获得包含酶制剂事实的有效正文；央视空壳页面不能通过；原站403仍如实记录，替代来源可追溯。分别统计有效正文率与耗时，而非只看HTTP成功率。

### 3. 日期存疑要补证，不能随便放行或直接丢掉

现状：已有正文因日期不能确认被挡住；也发现页面显示时间与元数据冲突、正文日期误取的情况。

拟改：

- 分开保存发布时间、事件发生时间、网页更新时间和采集时间。报告周期筛选仍以经过核验的发布时间口径为主，事件日期单独说明。
- 保存日期证据的位置、原始文本、解析值和来源；只读取文章主体关联的日期，不从推荐列表或任意正文数字取日期。
- 对可靠站点的文章头部日期做针对性解析和测试，并与元数据、URL、原始公告交叉核验；不能将所有 `content_header` 一律视为可信。
- 冲突资料进入待补证状态，通过原始公告、另一可靠报道或必要的人工确认解决。不得用采集时间填补发布时间。
- 将旧论文、官网技术能力等单列为背景材料，明确日期和用途；不得冒充当期新闻，背景材料仍需满足权限和事实核验要求。

验收：食品伙伴网样本不再误取另一日期；罗盖特日期冲突不会被静默选值；能证明日期的标准公告可正常采用，不能证明的明确待核验。

## 三、第二阶段：让每天的搜索真正覆盖业务问题

### 4. 同类对象分组保留，增加覆盖检查和短查询补查

不改回“每个对象 × 每个关键词 × 每个网站”全量搜索。保留分组节省成本，但不再认为一组返回结果就等于所有对象完成有效覆盖。

拟改：

- 按业务主题、对象类型和语言分组，避免将不相关的公司与政策投诉词混在一条查询里；每个对象都获得必要的名称和主题词预算，不能被前面对象挤掉。
- 博查使用简短明确的检索词；豆包使用有边界的研究问题，说明对象、主题与时间窗。两者不必机械共用同一条长查询。
- 记录每个对象“是否查询、是否命中、是否有有效事件”。没有消息不等于失败，但长期零命中需要检查查询、收录和对象别名。
- 对未覆盖对象和专题做有限次数的单对象、中文/英文或站点限定补查；每次保存查询和结果，复跑优先复用检查点。
- 每日发现使用可配置的短期重叠窗口，降低搜索收录延迟带来的遗漏；通过现有事件去重防止重复入库。报告自身的统计周期保持不变。
- 显式记录两个渠道实际使用的时间语义，检索窗口不替代入库时间核验。

验收：与旧查询在相同时间、预算和可用来源下对照，检查对象覆盖、有效独立事件和噪声比例。不能以返回条数更多作为唯一通过标准。

### 5. 增加研究型补查，弥补一般新闻查询的盲区

| 公司 | 优先研究问题 | 业务边界 |
| --- | --- | --- |
| 健源 | 淀粉糖竞对、果糖及玉米加工糖类、工艺与酶效率、客户配方与经营、替代甜味剂、标签法规 | 茶饮、乳品、烘焙等下游动态可以有用，不要求标题必须出现“玉米”或“果糖”；甜蛋白可作甜味剂替代参照，不等于公司生产蛋白 |
| 御馨 | 蛋白竞对、蛋白应用与去腥改性、客户新品和应用布局、非转基因大豆供需品质 | 普通植物油、压榨和饲料豆粕动态不纳入核心内容；不能把所有大豆新闻等同于蛋白业务机会 |

先合并全部已有材料再判断缺口，避免某一批没看到就误判整期没有。缺口明确为“缺哪些对象、事件或证据”，再定向检索。官方技术页、专业媒体、论文摘要和合法开放全文按用途接入，不保证每个站点或付费全文都能获取。

补查设轮数、成本、截止时间上限；到限仍未找到，明确保留缺口，不编造或无限搜索。搜索只产生候选，必须经过相同的归属、正文、日期、去重和权限流程才能进入报告素材。

## 四、第三阶段：修复已经入库却写不出来的问题

### 6. 全部候选有处理结果，重要事件不能被固定名额挤掉

历史月报存在“加载588条、实际只初筛200条”以及通过105条再按配额压成50条的问题。这一段不修，扩大采集仍然可能白做。

- 移除静默截断，按事件分批处理并保存进度；预算不足标为未处理，可续跑，不能统计成不相关或已排除。
- 不以固定30至50条作为内容淘汰理由。正文按主题合并同事件与同类事实，控制阅读长度；补充证据可放附表，但附表不能代替关键事件正文覆盖。
- 每条候选都有可解释状态：待处理、待补证、重复归并、相关性排除、通过、已引用或未引用原因。一个事件多个URL只算一个事件。
- 对已审批高价值事件建立“事件到章节、段落和链接”的映射，自动检查遗漏；融通农发这类通过审批却没有写入的情况必须被发现。
- 回读与关键问题有关的原文片段，不只截正文前1200字；成本由按需取证控制，不靠丢掉事实控制。

验收：候选总数与各处理状态对得上；超过200条不静默丢失；所有已审批高价值事件有引用、合并或明确未用理由，不以100%原文堆砌为目标。

### 7. 公司事实、文章结构和引用共同约束写作

- 公司主营在产产品、研发方向、关注品类、客户及潜客分开记录，并附事实来源。不能把“关注赤藓糖醇”写成“公司已有赤藓糖醇产品”。
- 保留业务确认的周报、月报一级二级标题和飞书样式，不擅自换结构。与审阅偏好冲突的固定七条等数量要求，需业务确认后调整，不作为隐藏硬编码。
- 周报讲当期变化，月报跨事件归纳趋势、机会与风险；事实、推断和建议区分表达，不从客户自建工厂直接推导其对外销售。
- 将来源嵌入事件、项目或关键事实文字，不堆原文标题和“原文”按钮；检查链接实际内容是否支持相关句子。
- 将日期冲突、公司归属错误、核心数字无依据、关键事件遗漏列为具体核验项，不能被模型总分掩盖。未解决时保留审阅稿和风险，不绕过审阅直接正式发布。
- 保存系统初稿和审阅定稿，分类记录补资料、删错误、改分析、调结构；经业务确认后沉淀公司级规则，不能自动把每次人工改动变成全局规则。

## 五、哪些适合业务配置

优先扩展已有飞书简报计划的策略配置，不另建一套互相冲突的规则。实施前核对现有字段和覆盖优先级。

| 业务可调 | 系统负责，不作为普通业务开关 |
| --- | --- |
| 公司确认的别名、关注企业、研究专题与排除场景 | 权限校验、密钥、SSRF和站点熔断 |
| 新闻周期、背景资料是否使用、重点事件深度 | 日期证据、证据不足不能冒充事实 |
| 已确认模板、章节、篇幅偏好和导读数量模式 | 去重、并发安全、任务幂等和发送记录 |
| 每期补查开关；预算范围内的研究深度 | 管理员维护的渠道总预算、限流与成本上限 |

配置需要版本号、明确生效期和变更记录，每次生成保存实际配置快照。不能让调整今天的规则反向改变历史报告，或在正式发送前擅自重生成审阅中的文档。

## 六、可观测性与成本控制

管理页应分别显示搜索调用成功、原始线索、有效独立事件、归属成功、正文有效、日期已核验、正式入库、送审和报告采用数量。模型引用列表不计作已确认新闻；未处理不计作已筛除。

按渠道记录排队、请求、正文和模型评审耗时，保留真实Token与费用来源，不估算成已发生值。博查和豆包继续独立超时与并发预算；搜索完成后正文处理预算另计。

补查和重跑复用已验证正文、事件和查询检查点，避免重付相同搜索和摘要成本。稳定事实或旧背景材料按有效期复核，不每日重复抓取。

## 七、实施和验收顺序

| 阶段 | 工作内容 | 放行条件 |
| --- | --- | --- |
| A：离线回归 | 固定11月2日原始响应、正文和报告快照，加入同名公司、旧文和空壳正文反例 | 不依赖搜索结果每天变化，能稳定复现已证实缺陷 |
| B：已有资料不丢 | 别名归属、正文替代、日期补证、选材状态与覆盖检查 | 原有正例通过，误归属、日期冲突、假正文不能错误放行 |
| C：搜索补缺 | 短查询、小组覆盖、专题双语搜索、有限重叠窗口 | 在记录的预算内改善有效事件覆盖，并核算噪声和耗时；阈值由基线与业务共同确定 |
| D：报告对照 | 两家公司各两期周报、一期月报，以相同素材对照旧流程与新流程 | 业务确认事实正确、结构一致、关键事件覆盖更完整，记录返工时间与具体改动量 |
| E：有限上线 | 只对选定计划启用，生成不发送或仅经确认进入审阅 | 单独确认发布和推送范围，保留旧策略与回退开关，不修改收件人和发送日历 |

离线回放、现在重新搜索和历史当天的真实召回是三种不同证据，统计时分别标明。不能拿今天找到的新闻证明历史当天必然能搜到，也不能把8个诊断样本的命中率当平台整体召回率。

正式部署另行执行仓库既有发布流程；本方案不代表已授权部署、重生成现有文档或发送消息。

## 八、建议先确认的业务事项

1. 两家公司关注边界及哪些资料可作为历史背景。
2. 保留的周报、月报结构，以及导读条数是否可随当期有效事件调整。
3. 哪些事件属于必须覆盖，哪些内容允许简写或进入证据附表。
4. 允许的补查成本、生成截止时间及待核验内容的审阅方式。

建议第一批先完成B阶段，并同步补齐处理状态。理由是这些问题已由实测证实，修复后能直接减少“搜过了却没用上”的损失，再投入更多搜索成本才更有价值。

## 九、完整目标流程与现有系统的关系

完整流程：

公司事实与编辑规则 → 单期任务及时间范围 → 日常采集与事件入库 → 素材清点 → 全量分批判断 → 研究提纲与缺口检查 → 按需补查和原文回读 → 章节研究 → 主笔整稿 → 独立核验与局部修订 → 飞书格式渲染 → 人工审阅 → 正式发布 → 修改复盘与规则沉淀。

系统当前已经有周报策划、专题研究、主笔、审阅和修订；月报已经有多策略候选、三类审阅和整稿合成。本方案不是再叠一批角色，而是让既有角色使用同一份可核验事实、留下可对账的产物，并修复阶段间丢失信息的问题。

| 阶段 | 必须形成的产物 | 不能出现的情况 |
| --- | --- | --- |
| 任务初始化 | 公司、周期、模板、策略、权限和发送安排的版本快照 | 临时生成改变后续计划；生成日被模型写成素材结束日 |
| 日常发现与入库 | 事件主体、原始来源、正文、日期证据、对象关联 | URL很多就当事件很多；重试重复入库 |
| 素材清点 | 候选总表及各阶段状态 | 只看前200条却说全部已分析 |
| 资料研究 | 事实记录、原文证据、重要事件清单、明确缺口 | 用AI写的业务启示当原文事实 |
| 提纲与写作 | 章节提纲、事件覆盖映射、带来源的完整初稿 | 把逐篇摘要拼成文章；有价值材料因固定名额消失 |
| 质量核验 | 具体问题、证据位置、处理结果 | 模型给90分就默认全部正确 |
| 飞书审阅 | 原始初稿快照、同一文档、审阅权限及版本 | 重生成覆盖审阅组修改；泄漏未授权素材 |
| 正式发布 | 确认的文档版本、接收人权限、卡片及回执 | 发送阶段再次生成；只发卡片不授权 |
| 复盘 | 修改类型、真实补充资料、待确认规则和回归样本 | 人工改过就当所有事实正确，自动改全局Prompt |

## 十、生成前：把任务、公司和素材准备正确

### 1. 确定本期任务，所有地方共用同一份信息

本期实例固定公司、报告类型、素材开始与结束时间、数据截至时间、实际生成时间、文档标题、审阅与正式推送安排，以及公司规则和模板版本。

- 时间按Asia/Shanghai计算，数据库查询使用明确的起止边界。周二生成的常规周报可沿用上周二00:00至本周二00:00的半开区间，展示为上周二至本周一；例外按本期显式设置，不让模型自行推算。
- 月报区分完整自然月和月底提前生成稿。提前生成时必须写明实际数据截至时间，不把尚未到来的日期当成已覆盖资料；是否补齐月底剩余数据由计划配置和审阅安排决定，不能偷偷覆盖已审文档。
- 标题、周次、头部周期、卡片和计划列表使用同一套确定性计算。月内周次口径由业务确认并做跨月测试，不由不同模型分别计算。
- 生成、审阅、正式发送分别排程。只生成、只发本人、只发审阅组、正式组暂停和单期改时间，必须是独立明确的控制项。

### 2. 公司事实与阅读偏好分开

公司事实包括已确认的产品、生产能力、业务主体、集团关系和客户关系；阅读偏好包括关注行业、技术和客户动态。关注一个品类不等于公司生产它。

两家公司读取独立配置，但允许同一事件分别关联不同价值。例如某茶饮新品：健源可关注甜味配方、客户经营和糖浆需求；御馨只有存在可核验蛋白应用等依据时才采用，不能套同一段“有利于公司”的分析。

同一事件出现在两份报告不必然是错误，关键是两份报告是否各自有事实支撑的业务关系。禁止仅靠通用关键词或由模型猜测的销售机会决定归属。

### 3. 冻结素材快照并全量清点

报告开始时冻结素材集合及内容版本；补查结果另存增量并生成新的素材快照。后续阶段明确使用哪个版本，避免执行中数据变化导致数量对不上。

先按权限和周期取数，事件级去重后逐批处理全部候选。读取权限撤销或来源被纠正时，标记受影响报告，发布前再次校验，不能用旧快照绕过当前权限。

对每个事件记录是否正文完整、日期可靠、与公司何种业务相关、是否重复、是否需补证。计算资源耗尽时保存检查点并标为未完成，不自动当成筛选完成。

## 十一、选材与研究：从文章列表变成有证据的事实

### 1. 为每个事件建立事实记录

事实记录至少包含：事件ID、主体、动作、发布时间与事件时间、关键数字及单位、所处阶段、来源URL、支持该事实的原文位置或片段、公司关联依据、适用章节、证据等级和未确认项。

例如产能必须区分规划、开工、试产和投产；财务必须区分收入、利润、同比和环比；技术必须区分实验结果、中试和商业化。无法从材料确认的字段保持未知，不能由模型补齐。

摘要用于导航，原文证据用于写作。模型对重要公告和技术信息应能按问题回读相关段落，必要时读取全文；本地已取得的全文不能一直只传前1200字。

### 2. 选材看业务价值，不以篇数压缩内容

采用理由可以是直接业务变化、竞对变化、客户经营与应用信号、成本或合规影响，也可以是明确的替代技术。分别说明相关性、事件重要性和证据强度，不将相关性分数直接当重要性。

通过的材料分成重点展开、合并综述、背景参照和证据附表。未采用需说明重复、过期、与业务无关或证据不足等原因，不能只有“名额不足”。背景和附表不能代替核心事件正文覆盖。

同主题可以合并叙述，但不同事件、不同公司和不同时期的数字必须各有归属；避免为了简洁把不同项目混成一个项目。

### 3. 先做全局缺口检查，再补资料

研究协调环节核对全部已通过素材，形成“已有事实、待解释问题、缺少证据”的清单。只有明确缺口才触发补查：缺公司动态就查公司，缺工艺细节就回原文或研究机构，缺政策日期就查发布机关。

补查结果进入相同的数据核验和权限链路，不允许研究模型直接把未落库、未验证的网页内容写进正式报告。以受控研究任务写入并保留来源，不另建绕过审计的临时入口。

补查到预算或截止时间仍无结果，则留下真实缺口。没有技术消息不能伪造，没有重大原料变化不必塞进无关行情凑章节。

## 十二、文章生成：研究、组织、成文分别负责

### 1. 策划阶段先给提纲，不直接写整篇

策划输入是本期公司规则、固定模板、事实记录和历史已确认写作样例。输出每个章节要回答的问题、核心判断候选、支撑事件ID、需要解释的矛盾及必写事件清单。

所有一级、二级标题遵循业务确认的模板。研究主题可在既有章节内组织，不擅自改变领导确定的文章结构；模板没有足够资料时按业务确认方式说明，不为形式完整强凑。

### 2. 专题研究角色交付证据和分析，不各自随意写成稿

复用现有政策、竞对、客户、技术和原料研究角色。每个角色输出：重要变化、证据、与目标公司的联系、可能影响及前提、与其他主题的联系、尚不能判断的事项。

允许并行研究，但共用同一事实集合与命名口径。必须由主笔统一段落、衔接和用词，不能把五个角色的段落直接首尾相接。

专题角色可提出补查请求，由协调环节去重和分配预算，避免五个角色重复搜索同一篇文章。模型无权自行修改生产配置、授权、文档或发送消息。

### 3. 主笔按逻辑组织文章，而不是逐条改写摘要

一段文字应围绕一个问题组织：发生了什么变化，哪些事件支持，分化在哪里，对目标公司可能有什么影响，哪些条件尚待确认。不是每段都机械套四句模板，也不是每条新闻都强行给出行动建议。

相关事件在一个段落中自然归纳，事件名或项目短语直接挂超链接。不在句末再追加一遍文章标题，不连续堆“原文”“来源”。不同结论由不同来源支持时分别挂链接，不能用一个链接担保整段所有数字。

上下游需求、竞争冲击、采购机会等属于推断时，保留依据和前提；不能将“可能增加需求”写成“已带来订单”。没有证据的确定性结论必须删除或降为待验证判断。

### 4. 周报和月报不是长短两个版本

| 维度 | 周报 | 月报 |
| --- | --- | --- |
| 主问题 | 本周发生了哪些值得关注的变化 | 本月多个变化共同说明了什么，以及是否有分化 |
| 组织方式 | 当期事件与短期变化，重点解释新增信息 | 跨周归并、公司或产业环节比较、趋势及其证据 |
| 重点内容 | 新项目、新品、政策变动、客户和竞对最新动作 | 市场变化、竞争格局、客户应用、工艺进展与原料因素的综合判断 |
| 历史材料 | 少量用于解释事件背景，明确不是本周新增 | 用于比较和持续跟踪，历史数字须有同口径依据 |
| 避免 | 为凑七条加入弱相关消息 | 把四份周报拼起来，或单纯扩写每篇摘要 |

月报多稿生成可保留为可选策略，但各稿必须使用同一事实与模板版本。不同模型意见不能互相充当来源，最终合成不能创造候选稿中都没有证据的新事实；多稿并不自动等于高质量。

### 5. 输出完整草稿及内部覆盖映射

主笔同时输出正文和内部映射：每个章节用了哪些事件，关键结论由什么证据支持，重点事件遗漏或合并的理由。映射给系统检查和审阅查看，不强制铺进报告正文。

不强制所有候选逐条出现在文章中；要求所有重点且可用的事件得到处理和解释。既保证信息量，也避免冗长的新闻列表。

## 十三、质量检查与自修复

### 1. 四类检查分工

| 检查 | 主要方式 | 检查内容 |
| --- | --- | --- |
| 格式与一致性 | 确定性代码 | 模板标题、周期、公司名、卡片标题、链接结构、必需区块和标签样式 |
| 事实与证据 | 结构化对照结合独立模型 | 数字单位、主体归属、发生阶段、日期、原文是否支持句子 |
| 业务与表达 | 独立审阅角色 | 健源/御馨是否串题，是否无依据夸大机会，是否拼凑和重复 |
| 覆盖与缺口 | 全量事件映射 | 高价值事件有没有漏写，各类未采用理由是否成立，是否缺重要专题 |

事实审阅不能只看草稿和压缩摘要，需要能访问原文证据；覆盖审阅必须看整期候选和审批结果，不能只检查最后入选的50条。

### 2. 按问题返回上游，不盲目重写全篇

- 漏关键事件：返回提纲/主笔补入或解释，不重新搜索已经存在的材料。
- 日期或核心数字无依据：回到证据核验，必要时补查；查不到则删除对应断言或保留明确不确定性。
- 公司混淆：检查对象关联与公司规则，不能只在成稿中替换公司名。
- 段落拼凑：由主笔重组该段，保留已验证事实和链接。
- 仅格式错误：由渲染或格式修复处理，不再调用完整研究流程。

每次修复保存问题ID、修改范围、前后版本和再检查结果。循环次数、总Token和截止时间受控；超过预算保留失败原因和草稿，通知计划管理员，不能循环到调度阻塞。

### 3. 质量放行规则

核心事实错误、公司归属错误、未授权内容和关键日期冲突不能被高总分抵消。一般表达建议不必硬阻断，但要可见。证据不足的段落不能以“审阅组会删”为理由进入可正式发布状态。

仅生成草稿、发送审阅和正式发布分别判定。未通过正式门槛的草稿可按授权供审阅，但不得因为任务运行成功就自动正式发送。门槛和正式发布政策的改动须明确配置并经业务确认。

## 十四、飞书文档生成与人工审阅

### 1. 内容和格式分离

模型负责正文结构与语义链接，确定性渲染负责飞书标题层级、头部说明、居中样式、分隔线、分类标签底色和链接属性。不要指望提示词让Markdown的三个横线自动变成飞书分隔线。

写入后回读文档区块，检查标题数量、标签颜色、链接目标、正文缺段和重复区块。用已确认报告样例核对视觉效果，不能只验证接口200。

### 2. 保留同一篇审阅与正式文档

保存系统初稿正文及结构快照、文档ID、生成规则版本、素材版本。审阅组在这一篇飞书文档中修改，正式组随后收到同一链接，正式阶段不重生成、不换链接、不覆写正文。

原文档重生成必须显式操作，并先归档审阅中的版本、检测他人修改冲突。系统更新规则只标记“内容配置已变化”，不能后台替换已经审阅的文档。

### 3. 审阅反馈如何进入系统

支持回读当前文档与初稿比较，将修改识别为新增事件、补数字、纠错、业务判断、语言结构或样式调整。审阅新增资料有链接时回到采集核验；无链接时标记需提供依据，不直接转成事实。

“已审定”不应仅由收到卡片或编辑过文档推断。可设计明确审定状态，并记录确认人、时间和文档版本；是否将人工审定设为正式发布的必需条件，由业务确认，不擅自改变现有自动发送政策。

## 十五、正式发布、授权与调度可靠性

### 1. 发送前核查，不再生成正文

正式任务检查：本期未暂停、时间已到、文档存在、质量与审阅政策满足、来源权限仍有效、接收名单正确，且接收人拥有相应文档阅读权限。

先授权并检查组织密级策略，再发卡片。授权失败者单独记录，不能降低L3密级或改为公开链接规避权限。正式阅读与审阅编辑权限分开，不因先前收到审阅消息就自动跳过正式推送；是否跨组去重必须是明确策略。

卡片使用版本化模板和本期统一元数据；同一发送阶段不同接收人使用同一内容。审阅卡片是否展示正式版文案由计划设置，不能临时编写另一套措辞。

### 2. 生成和发送采用独立状态

建议分别记录生成状态、文档版本、审阅状态、审阅发送状态和正式发送状态，避免一个“成功”掩盖正文未完成或部分人无权限。

以计划、公司、报告类型和周期标识本期实例；以本期实例、发送阶段和接收人作为发送幂等依据。审阅版重生成不能自动触发正式组重复发送；主动补发需要显式记录。

保存单条消息ID、卡片版本、收件人和回执；采用批量接口时也要保存可用于逐人查错的回执与批次ID，不能只保存总成功数。超时但发送结果不明时先对账，不盲目重发。

### 3. 暂停、改时间和服务重启可控

- 单期改时间不影响后续常规计划，暂停正式组不暂停审阅组，取消发送不等于删除文档。
- 任务执行前再次检查取消和版本状态；同一任务有锁和执行租约，重启或多进程不能重复生成、重复发送。
- 设置错过时间后的处理策略与最晚发送期限，避免服务恢复后突然补发已取消或过期报告。
- 生成失败不会让发送任务自动选择别的周期或旧文档；显示失败并通知管理员处理。
- 发送前保存版本校验结果；若审定后文档又修改，则按配置要求重新确认或再次核验。明确共享文档是可继续编辑的活文档，归档快照用于追溯当时发送内容。

## 十六、反馈学习：逐期减少返工

系统初稿、审阅修改稿、正式发送快照和修改理由共同构成复盘依据。不同阶段快照缺失时标明不可比较，不从当前文档猜出历史版本。

每条重要修改区分原因：

| 修改类型 | 应修复的位置 |
| --- | --- |
| 补入系统未发现的新闻 | 监测对象、专题查询和来源覆盖 |
| 补入搜到却未入库的资料 | 正文、日期、归属或评审流程 |
| 补入已入库但未写的事件 | 选材截断、提纲和覆盖核对 |
| 改数字、公司、产品或时间 | 公司事实、证据提取和事实审阅 |
| 改分析逻辑、比较对象 | 专题研究和主笔规则 |
| 改结构、标签和超链接 | 模板与飞书渲染 |

经业务确认的编辑偏好沉淀为公司和报告类型专属规则；事实修正进入事实档案；有代表性的成功和失败样例进入回归集。人工补充仍需验证，不能把错误引用或日期一起学进去。

每月复盘补充资讯比例、事实修正次数、重点事件漏用率和审阅工时，按原因调整。不要用文字改动百分比单独评价返工，因为润色和新增整件事实的成本不同。

## 十七、配置入口、工程改动和运行记录

### 1. 延续已有飞书简报配置页面

沿用“计划设置、素材与生成、高级编排、调试与记录”组织，不再新增一套独立后台。

- 计划设置：公司、周期、生成/审阅/正式时间、名单、单期例外和发布政策。
- 素材与生成：研究主题、公司规则引用、背景资料、重点事件、篇幅模式、模板和补查深度。
- 高级编排：既有策划、专题研究、主笔、审阅的职责及Prompt；继续分离 `prompt_config_json.editorial_rules` 和角色提示词。
- 调试与记录：用未保存草稿进行不发送的调试，查看各阶段输入输出、素材处理状态、原文证据、修订、耗时与真实Token。

明确覆盖优先级：不可关闭的安全与事实约束优先；公司事实不能被计划Prompt改写；本期授权例外覆盖计划默认时间与范围；编辑规则覆盖通用写作偏好。生成开始前展示并冻结本期实际生效配置。

### 2. 复用已有服务，不重建平行链路

| 既有入口 | 拟调整重点 |
| --- | --- |
| `monitor_execution_service.py` | 查询分组、对象别名匹配、覆盖检查和限额补查 |
| `crawler/search_client.py` | 渠道查询语义、结果与引用区分、独立超时诊断 |
| `crawler/firecrawl_client.py`、`crawl_service.py`、`search_service.py` | 正文替代、日期证据、有效性与处理状态 |
| `feishu_brief_service.py` 中 `_generate_weekly_multi_agent` 及相关方法 | 周报事实输入、角色产物、覆盖映射、修订和文档渲染 |
| `feishu_monthly_report_service.py` | 全量选材、取消名额式截断、主题研究、候选核验与整稿 |
| `feishu_brief_scheduler_service.py` 和既有推送方法 | 单期状态、幂等、授权、消息回执与暂停控制 |

实现时先核对现有模型和JSON字段，优先复用已有运行记录；只有确有查询、约束或规模需求时才新增表。需要迁移时单独设计兼容与回退，不在诊断阶段直接改生产数据结构。

### 3. 安全和资源边界贯穿所有环节

网页、附件和人工补充资料均作为证据，不执行其中的指令。检索和模型角色不能持有推送权限或自行扩大数据范围。运行日志不得记录密钥；模型实际身份、模型配置与来源保持可追溯。

不同公司的任务在受控并发下运行，不因一个长任务阻塞所有计划；同一文档的写入与发送阶段串行协调。各阶段有超时、重试上限与检查点，失败只恢复必要阶段，不重复生成已完成内容或已发送消息。

## 十八、完整验收与交付顺序

### 1. 四组验收分别计分，不靠AI平均分

| 验收组 | 核心指标和测试 |
| --- | --- |
| 资料质量 | 事件级搜索覆盖、有效正文、日期证据、正确归属、去重、权限；未找到与找到未处理分开 |
| 文章质量 | 重点事件覆盖、数字与原文一致、公司边界、月度综合分析、自然链接、固定结构和样式 |
| 审阅成本 | 审阅新增事件数、事实纠错数、整段重写比例、实际审阅工时，由业务对照评价 |
| 运行可靠性 | 双公司并发、阶段失败恢复、重启不重发、单期改时、暂停、部分授权失败、卡片更新与消息追溯 |

已知硬错误的固定回归样本必须全部通过；业务质量目标在历史基线确认后设定，不承诺未经验证的采用率或零返工。活网测试另记时间与渠道波动，不替代可重复的固定样本测试。

### 2. 完整交付分五批

1. 固定历史样本和评判标准，建立可对账的素材、证据、初稿和审阅快照。
2. 修别名、正文、日期、静默截断和报告覆盖遗漏，先把现有资料利用好。
3. 完善公司规则、事实记录、策划研究、主笔整稿、独立审阅与局部修复，产出两家公司可对比的周报和月报。
4. 接入有预算的专题补查与业务配置，同时完善飞书样式、同文档审阅、权限、发送幂等及回执。
5. 先离线对照，再不发送试运行，再按明确批准范围审阅试点，验收后才接入正式定时发布。

每批均给出代码变更、回归结果、成本耗时、业务待确认项和回退办法。上线必须走既有发布脚本，不改变本期报告、收件人和时间安排，除非得到针对该操作的明确指令。

最终验收目标：业务人员能看见“这条资料为什么没用”“这个结论依据什么”“本期用的哪版规则”“谁收到了、是否有权限”；审阅组修改能被有针对性地沉淀，下期不再反复出现同类问题。
