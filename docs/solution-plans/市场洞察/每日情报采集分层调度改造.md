# 每日情报采集分层调度改造

## 评审前正文补抓

搜索平台返回的标题和摘要只用于第一阶段预筛。预筛通过后，系统按相关性为每个监测任务选取默认 3 条高价值结果，使用 Firecrawl 或适配器已有正文补全原采集记录，再基于正文生成摘要、机会、风险并进行最终 AI 评审。

普通媒体、搜索和转载来源没有取得至少 200 字有效正文时只能进入候选线索；政府网站、交易所、专利机构等可信结构化来源可使用公告摘要例外转正式。正文补抓采用系统级并发池，默认并发 6，失败、跳过和成功数量写入任务的 `fulltext_summary`，避免目标网站故障拖垮整轮调度。

2026-07-14 使用“玉米深加工与功能糖政策市场”执行真实受控测试：百度返回 2 条，验证码页面被归档；国家粮食和物资储备局文章的 Firecrawl 请求返回 408 后，受控直接 HTTP 降级成功抽取 1368 字正文，并重新生成摘要、更新正式情报、资产向量和图谱。该测试证明搜索预筛、正文补抓、失败降级、最终评审和资产更新链路可以连续运行。

## 改造原因

旧调度每轮只取 `INSIGHT_SCHEDULER_BATCH_LIMIT=5` 个到期监测对象，博查和豆包的分组查询也只覆盖这 5 个对象。当前有 150 个启用对象时，一轮无法支撑日报，且垂直渠道长期按固定顺序截断，后排渠道容易得不到执行机会。

## 当前策略

1. 每日发现覆盖全部启用且非手工监测对象，不受深挖批量上限限制。
2. 百度资讯对每个对象每天执行，默认读取近 3 天作为滚动补漏窗口；相同 URL 在 LLM 初筛前去重，不会重复进入候选和资产链路。
3. 博查和豆包按企业关系、主题和主要模块分组；博查每组默认不超过 8 个对象，豆包联网搜索每组默认不超过 4 个对象。两个渠道并发执行，再把结果反向归属到具体监测对象。
4. 信号深挖优先处理当日发现新信号的对象，已到期对象补位；只执行独立网站适配器，批量上限默认 5。
5. 头条、搜狐、腾讯、新浪财经和重点食品行业渠道进入每日轻量采集池，不再依赖少量到期对象轮转；其他垂直渠道仍按日期和监测对象轮转，周频、月频渠道按渠道 ID 分片到不同日期。
6. 新增命中继续经过历史去重、AI 初筛、AI 自动评审、正式情报、资产、向量化和图谱；到期日报在当轮发现和深挖之后生成。
7. 定时日报优先使用最近 24 小时新增情报，素材不足时允许读取近 3 天作为背景，但生成提示会强制区分“今日新增”和“近三日延续信号”；周报和月报分别限定近 7 天、近 30 天。

## 配置

- `INSIGHT_SCHEDULER_DAILY_DISCOVERY_ENABLED`：是否开启每日全覆盖发现。
- `INSIGHT_SCHEDULER_DAILY_DISCOVERY_FRESHNESS`：每日滚动补漏窗口，默认 `3d`。
- `INSIGHT_SCHEDULER_BAIDU_CONCURRENCY`：百度并发，默认 `1`，同一出口严格串行。
- `INSIGHT_SCHEDULER_BAIDU_COOLDOWN_MIN_SECONDS/MAX_SECONDS`：百度对象间随机冷却，默认 5-10 秒。
- `INSIGHT_BAIDU_ANTIBOT_COOLDOWN_SECONDS`：命中百度安全验证、验证码域名或 HTTP 403/429 后的熔断时长，默认 21600 秒；熔断期间不再请求百度，但其他发现渠道继续执行。
- `INSIGHT_SCHEDULER_BAIDU_SPREAD_ENABLED`：是否把百度从凌晨主采集拆为全天分片，生产默认开启。
- `INSIGHT_SCHEDULER_BAIDU_SLOT_INTERVAL_SECONDS`：百度分片时间槽间隔，默认 600 秒；一天形成 144 个槽，监测对象按稳定 ID 取模分配，每个对象每天一次。

2026-09-02 反爬治理补充：服务器出口曾被百度重定向到 `wappass.baidu.com` 安全验证页，旧逻辑因页面仍返回 HTTP 200 而误记为成功。现已增加验证页识别、Redis 持久化熔断和 `baidu_spread_tick` 独立任务日志；凌晨主任务只记录百度延期数量，不再批量发起 144 次请求。后端重启后从下一个时间槽继续，不追赶停机期间的历史槽，避免恢复时形成突发流量。
- `INSIGHT_SCHEDULER_GROUPED_BATCH_SIZE`：博查单组对象数，默认 `8`。
- `INSIGHT_SCHEDULER_GROUPED_AI_BATCH_SIZE`：豆包联网搜索单组对象数，默认 `4`。
- `INSIGHT_SCHEDULER_GROUPED_BATCH_LIMIT`：单轮最大分组数，默认 `100`。
- `INSIGHT_SCHEDULER_GROUPED_AI_TIMEOUT_SECONDS`：豆包单次分组搜索总时限，默认 `240` 秒。
- `INSIGHT_DOUBAO_SEARCH_CONNECT_TIMEOUT_SECONDS`：豆包连接时限，默认 `15` 秒。
- `INSIGHT_DOUBAO_SEARCH_READ_TIMEOUT_SECONDS`：豆包流式读取时限，默认 `240` 秒。
- `INSIGHT_SCHEDULER_DAILY_ADAPTER_CHANNEL_CODES`：必须每日执行的重点站点适配器。
- `INSIGHT_SCHEDULER_DAILY_ADAPTER_HIGH_COVERAGE_CODES`：每日覆盖全部核心业务主题的综合站点，默认头条、搜狐、腾讯和新浪财经。
- `INSIGHT_SCHEDULER_DAILY_ADAPTER_CONCURRENCY`：重点站点跨渠道并发，默认 `2`；同一渠道始终串行。
- `INSIGHT_SCHEDULER_DAILY_ADAPTER_TOPIC_LIMIT`：普通重点渠道每天轮转的业务主题数，默认 `2`。
- `INSIGHT_SCHEDULER_BATCH_LIMIT`：仅限制信号深挖，不再限制每日发现。

## 验证结果

- 当前 150 个启用对象全部进入百度每日发现。
- 博查和豆包形成 22 个分组，覆盖 146 个有效对象；其余 4 个占位配置仍由百度逐对象处理。
- 模拟全覆盖结果为：检查 150、百度尝试 150、百度成功 150。
- 后端 `py_compile`、Insight 范围 `ruff check` 和前端 `pnpm build` 通过。

- 新增生产每日策略补采入口：`uv run python scripts/insight_run_daily_discovery_once.py --start-date 2026-07-10 --end-date 2026-07-13`。
- 150 个启用监测对象全部进入百度发现，成功 148、超时 2；两个超时对象随后单独重试成功，本时间窗内均无新增命中。
- 博查和豆包分别执行 22 个合并批次，全部成功；博查原始命中 161 条，豆包原始命中 137 条，合并结果按监测对象反向归属后继续进入统一链路。
- 本轮主任务命中 131 条并生成 131 条候选；清理越界、无日期和异常链接后，有效新增正式情报 47 条，7 月 10 日 16 条、11 日 7 条、12 日 3 条、13 日 21 条。
- 47 条新增正式情报均取得不少于 200 字正文；当前有效新增资产 59 条，均已完成向量化和图谱处理。
- 运行中发现并修复两个边界问题：精确时间参数写入任务 JSON 时需使用 Pydantic JSON 模式；正文补抓重新识别发布时间后必须再次执行时间窗过滤。豆包返回链接增加 HTTP(S) 清洗，阻止模型 JSON 黏连到 URL。

## 观察项

- 首轮近 3 天补漏的 Token 和候选量通常高于后续稳定日。
- 百度并发不宜超过 5；出现验证码或封禁时应增大冷却，而不是提高重试频率。
- 上线后一周重点观察每日覆盖数、发现量、候选量、渠道失败和 Token，再调整分组大小及深挖批量。

### 2026-07-30 豆包联网搜索超时修复

- 7 月 30 日凌晨运行中，豆包 22 个分组仅 2 个完整成功、1 个部分成功，其余分组主要因 90 秒总时限被取消，实际只留下 6 条线索。
- 豆包不再与博查共用 8 对象分组，默认缩小为 4 对象；首次失败后继续按 2 对象拆分补偿。
- 调度总时限和流式读取时限均提高到 240 秒，连接时限单独保持 15 秒，避免连接故障长时间占用任务，同时给模型联网检索、整理和流式输出留出完整时间。
- 豆包总并发保持 2，拆分补偿并发保持 2，避免超时后瞬间放大请求并触发服务端排队或限流。

### 2026-07-30 重点渠道每日采集修复

- 检查发现头条、搜狐、腾讯、食品伙伴网等渠道虽然标记为每日和已接入，但仍由到期监测对象与垂直渠道预算轮转控制，最近一次实际成功运行多数停留在 7 月 14 日，无法形成每日覆盖。
- 新增重点渠道每日轻量采集池。头条、搜狐、腾讯和新浪财经每天覆盖果葡糖浆与麦芽糖浆、植物蛋白、豆粕粮油、玉米深加工、饮料茶饮、食品安全六个核心主题；FoodDaily、食品伙伴网、咖门、小食代、食业头条、新营养、云糖、粮油市场报、新蛋白、新华网、人民网、央视等渠道每天轮转至少两个相关主题。
- 每个渠道内部严格串行，不同渠道默认并发 2；每次运行继续写入适配器审计、失败原因、耗时、命中数和候选数。每日轻量池负责的渠道不再在同一轮周期深挖中重复执行。

### 2026-08-01 发布时间可信度修复

- 发现百度搜索结果可能把“刚刚”解析为采集时间，正文补抓未取得发布日期时又沿用了该时间，导致 2020 年、2025 年旧文进入 2026 年当日正式情报。
- 采集记录新增发布时间证据语义：搜索结果时间标记为未核验；页面元数据、JSON-LD、文章 URL 和明确文章头部时间才可标记为已核验。正文中出现的项目日期、政策日期和历史事件日期只作弱线索。
- 正文补抓后重新执行每日 freshness 或精确起止时间过滤；普通媒体无已核验发布时间时只能保留候选，且不得参与正式情报事件归并。
- 已核对并同步修正 5 条历史误标记录，主情报、来源证据、采集结果和资产发布时间保持一致，其中界面网相关文章恢复为 2020 年、2025 年真实日期。
