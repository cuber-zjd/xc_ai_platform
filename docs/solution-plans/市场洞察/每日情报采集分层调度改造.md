# 每日情报采集分层调度改造

## 评审前正文补抓

搜索平台返回的标题和摘要只用于第一阶段预筛。预筛通过后，系统按相关性为每个监测任务选取默认 3 条高价值结果，使用 Firecrawl 或适配器已有正文补全原采集记录，再基于正文生成摘要、机会、风险并进行最终 AI 评审。

普通媒体、搜索和转载来源没有取得至少 200 字有效正文时只能进入候选线索；政府网站、交易所、专利机构等可信结构化来源可使用公告摘要例外转正式。正文补抓采用系统级并发池，默认并发 6，失败、跳过和成功数量写入任务的 `fulltext_summary`，避免目标网站故障拖垮整轮调度。

2026-07-14 使用“玉米深加工与功能糖政策市场”执行真实受控测试：百度返回 2 条，验证码页面被归档；国家粮食和物资储备局文章的 Firecrawl 请求返回 408 后，受控直接 HTTP 降级成功抽取 1368 字正文，并重新生成摘要、更新正式情报、资产向量和图谱。该测试证明搜索预筛、正文补抓、失败降级、最终评审和资产更新链路可以连续运行。

## 改造原因

旧调度每轮只取 `INSIGHT_SCHEDULER_BATCH_LIMIT=5` 个到期监测对象，博查和豆包的分组查询也只覆盖这 5 个对象。当前有 150 个启用对象时，一轮无法支撑日报，且垂直渠道长期按固定顺序截断，后排渠道容易得不到执行机会。

## 当前策略

1. 每日发现覆盖全部启用且非手工监测对象，不受深挖批量上限限制。
2. 百度资讯对每个对象每天执行，默认读取近 3 天作为滚动补漏窗口；相同 URL 在 LLM 初筛前去重，不会重复进入候选和资产链路。
3. 博查和豆包按企业关系、主题和主要模块分组，每组默认不超过 8 个对象；两个渠道并发执行，再把结果反向归属到具体监测对象。
4. 信号深挖优先处理当日发现新信号的对象，已到期对象补位；只执行独立网站适配器，批量上限默认 5。
5. 垂直渠道按日期和监测对象轮转；周频、月频渠道按渠道 ID 分片到不同日期，避免固定渠道长期占满预算。
6. 新增命中继续经过历史去重、AI 初筛、AI 自动评审、正式情报、资产、向量化和图谱；到期日报在当轮发现和深挖之后生成。
7. 定时日报优先使用最近 24 小时新增情报，素材不足时允许读取近 3 天作为背景，但生成提示会强制区分“今日新增”和“近三日延续信号”；周报和月报分别限定近 7 天、近 30 天。

## 配置

- `INSIGHT_SCHEDULER_DAILY_DISCOVERY_ENABLED`：是否开启每日全覆盖发现。
- `INSIGHT_SCHEDULER_DAILY_DISCOVERY_FRESHNESS`：每日滚动补漏窗口，默认 `3d`。
- `INSIGHT_SCHEDULER_BAIDU_CONCURRENCY`：百度并发，默认 `3`。
- `INSIGHT_SCHEDULER_BAIDU_COOLDOWN_MIN_SECONDS/MAX_SECONDS`：百度对象间随机冷却，默认 1-3 秒。
- `INSIGHT_SCHEDULER_GROUPED_BATCH_SIZE`：博查和豆包单组对象数，默认 `8`。
- `INSIGHT_SCHEDULER_GROUPED_BATCH_LIMIT`：单轮最大分组数，默认 `100`。
- `INSIGHT_SCHEDULER_BATCH_LIMIT`：仅限制信号深挖，不再限制每日发现。

## 验证结果

- 当前 150 个启用对象全部进入百度每日发现。
- 博查和豆包形成 22 个分组，覆盖 146 个有效对象；其余 4 个占位配置仍由百度逐对象处理。
- 模拟全覆盖结果为：检查 150、百度尝试 150、百度成功 150。
- 后端 `py_compile`、Insight 范围 `ruff check` 和前端 `pnpm build` 通过。

## 观察项

- 首轮近 3 天补漏的 Token 和候选量通常高于后续稳定日。
- 百度并发不宜超过 5；出现验证码或封禁时应增大冷却，而不是提高重试频率。
- 上线后一周重点观察每日覆盖数、发现量、候选量、渠道失败和 Token，再调整分组大小及深挖批量。
