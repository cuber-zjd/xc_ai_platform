# 经营智能-健源流失客户报表 CPT 预研

## 1. 预研对象

本次预研面向产业经营智能平台阶段一“经营数据 AI 分析”，先选取健源客户流失类月报作为经营数据样板。

正式 CPT 路径：

- `webroot/APP/reportlets/数据分析/健源报表/健源公司潜在流失客户情况月报（90天未发货）_v2.cpt`
- `webroot/APP/reportlets/数据分析/健源报表/健源公司流失客户情况月报（180天未发货）_v2.cpt`

同目录存在历史版本，可后续作为口径演进对比：

- `webroot/APP/reportlets/数据分析/健源报表/历史版本/健源公司潜在流失客户情况月报（90天未发货）.cpt`
- `webroot/APP/reportlets/数据分析/健源报表/历史版本/健源公司流失客户情况月报（180天未发货）.cpt`

## 2. CPT 结构结论

两张正式报表均为 UTF-8 XML CPT，根节点为 `WorkBook`，`xmlVersion=20170720`，`releaseVersion=10.0.0`。

共同数据集：

- `主数据`：核心客户流失识别 SQL，连接名 `XcTest`，参数 `year_month`。
- `流失客户额外数据`：`SELECT * FROM jy_lost_customer_extend`，承载人工判断、流失原因、具体原因和跟进措施。
- `ds1`：一年未发货的旧口径查询，当前 v2 页面未作为主绑定字段使用，可视为遗留数据集。
- 一个空的 `NameTableData` 数据集。

共同参数区：

- `year_month`：年月，日期控件，默认 `=today()`。
- `mara_group_desc`：产品，下拉控件。
- `customer_name`：客户名称，文本控件。
- 参数区还有若干 label 与提交按钮。

共同产品范围：

- `果葡糖浆`
- `麦芽糖浆`
- `差异化糖浆`

关键来源表：

- `jy_delivery_data_view2`：发货事实，包含客户、发货日期、发货量、物料组、产品、销售员等字段。
- `jy_customer_base`：客户主数据，包含市场、国家地区、应用领域、客户分类、业务员、产品要求等字段。
- `jy_latest_usage`：客户最新年用量。
- `jy_lost_customer_extend`：人工补充的流失判断、原因和跟进措施。

## 3. 口径发现

### 3.1 90 天潜在流失

报表名为“90 天未发货”，核心逻辑为：

1. 以 `year_month` 对应月份的月末日作为分析基准。
2. 找出近 90 天内有发货的客户。
3. 找出 90 天阈值之前一个月窗口内有发货的客户。
4. 在第 3 类客户中排除近 90 天已发货客户，得到“潜在流失客户”。

注意：SQL 注释写“90 到 180 天区间有发货”，但实际窗口是 `DATEADD(day, -90 - DAY(@month_end_day), @month_end_day)` 到 `DATEADD(day, -90, @month_end_day)`，即“跨过 90 天阈值的前一个月窗口”，不是全量 90-180 天未发货客户池。

报表列：

- 序号
- 产品
- 市场
- 客户名称
- 国家/地区
- 应用领域
- 产品要求
- 客户年用量(吨)
- 前年销量(吨)
- 去年销量(吨)
- 最后一次发货月份
- 最后月份发货量(吨)
- 未发货原因
- 跟进措施

### 3.2 180 天流失

报表名为“180 天未发货”，核心逻辑为：

1. 以 `year_month` 对应月份的月末日作为分析基准。
2. 找出近 180 天内有发货的客户。
3. 找出 180 天阈值之前一个月窗口内有发货的客户。
4. 在第 3 类客户中排除近 180 天已发货客户，得到“流失客户”。

同样需要注意：该报表实际更像“本月刚跨过 180 天未发货阈值的客户清单”，不是全量 180 天以上未发货客户池。

报表列：

- 序号
- 产品
- 市场
- 客户编码
- 客户名称
- 国家/地区
- 应用领域
- 产品要求
- 客户年用量(吨)
- 前年销量(吨)
- 去年销量(吨)
- 最后一次发货月份
- 最后月份发货量(吨)
- 是否流失
- 客户流失原因
- 具体流失原因(选其他,必填)
- 跟进措施

## 5. 可做的经营分析

### 5.1 基础经营指标

第一版可把两张 CPT 抽象为“客户流失风险”指标域：

- 潜在流失客户数：按月、产品、市场、国家/地区、应用领域、业务员统计。
- 流失客户数：按月、产品、市场、国家/地区、应用领域、业务员统计。
- 风险年用量：潜在流失或流失客户的客户年用量合计。
- 风险销量：潜在流失或流失客户去年销量、前年销量合计。
- 最后发货量：最后一次发货对应发货量合计或均值。
- 原因填写率：已填写原因客户数 / 风险客户数。
- 措施填写率：已填写跟进措施客户数 / 风险客户数。
- 确认流失率：`is_lost='是'` 客户数 / 180 天流失客户数。

### 5.2 归因拆解

适合做确定性拆解，不先让 AI 猜原因：

- 按产品拆解：果葡糖浆、麦芽糖浆、差异化糖浆的客户数、年用量、去年销量贡献。
- 按市场拆解：国内/国际，以及后续国家地区维度。
- 按客户价值拆解：用客户年用量、去年销量、最后发货量做风险权重。
- 按应用领域拆解：识别某类下游应用是否集中流失。
- 按业务员拆解：给销售管理提供待跟进列表。
- 按人工原因拆解：价格敏感、客户业务转型、多账户合作、淡旺季、产能/供应切换等。

### 5.3 风险客户清单

不只是复刻报表明细，而是给每个客户生成风险优先级：

- 高风险高价值：年用量高、去年销量高、近 90/180 天未发货、人工原因为价格或竞品切换。
- 可挽回客户：180 天报表中 `is_lost='否'`，但已有价格敏感或持续跟踪措施。
- 资料缺口客户：流失原因或跟进措施为空，优先提醒补充。
- 季节性客户：人工原因中出现淡旺季、多账户合作等，不直接当作真实流失。

### 5.4 经营信号卡

可生成如下信号：

- “2026 年 6 月健源潜在流失客户 42 户，麦芽糖浆年用量风险最高，年用量合计 38530 吨。”
- “2026 年 6 月 180 天流失客户 36 户，果葡糖浆 16 户，已有 3 户缺少跟进措施。”
- “差异化糖浆潜在流失 7 户、180 天流失 8 户，但人工原因和跟进措施覆盖为 0，需要优先补齐经营判断。”
- “国际市场 180 天流失客户数不高，但果葡糖浆年用量合计较高，应单独形成重点客户跟踪清单。”

## 6. 建议做成的页面形态

入口仍放在 Insight 的经营智能：

- 路径：`/insight/operation-intelligence`
- 菜单：`经营智能`
- 首个主题页：`健源客户流失分析`

页面第一版建议分四块：

1. 客户流失信号流
   - 按月展示 AI 生成的经营信号卡。
   - 每条信号包含指标、时间、产品、市场、证据数据和关联 CPT 路径。

2. 流失风险总览
   - KPI：潜在流失客户数、180 天流失客户数、风险年用量、风险去年销量、原因填写率、措施填写率。
   - 图表：产品分布、市场分布、原因分布、月度趋势。

3. 风险客户清单
   - 表格字段：客户编码、客户名称、产品、市场、应用领域、年用量、去年销量、最后发货月份、未发货天数、原因、措施、风险等级。
   - 支持按产品、市场、是否流失、原因是否缺失筛选。

4. 指标口径与报表证据
   - 展示指标定义、SQL 来源表、分析月份、阈值窗口和原始 CPT 路径。
   - 明确提示当前 CPT 是“跨阈值当月客户”，不是全量沉默客户池。

## 7. 实现建议

第一步不要直接把 CPT 作为在线查询入口，而是把 CPT SQL 口径沉淀为经营指标语义层：

- 指标域：`customer_churn`
- 数据源：SQL Server `XcTest`
- 初始分析月份：默认读取 `jy_lost_customer_extend` 最新期间，当前为 `2026-06`
- 口径类型：
  - `threshold_crossing_90d`：本月跨过 90 天未发货阈值。
  - `threshold_crossing_180d`：本月跨过 180 天未发货阈值。
  - 后续补充 `active_silent_pool_90d` / `active_silent_pool_180d`，表示全量沉默客户池。

建议后端先落地：

- `operation_metric_catalog`：经营指标目录。
- `operation_query_record`：问数和报表分析查询记录。
- `operation_signal`：经营信号卡。
- `operation_signal_feedback`：信号反馈。

建议服务：

- `backend/app/services/agent/insight/operation/metric_catalog_service.py`
- `backend/app/services/agent/insight/operation/customer_churn_service.py`
- `backend/app/services/agent/insight/operation/signal_service.py`
- `backend/app/services/agent/insight/operation/ai_analysis_service.py`

第一版接口：

- `GET /ai-api/v1/insight/operation/customer-churn/summary`
- `GET /ai-api/v1/insight/operation/customer-churn/customers`
- `POST /ai-api/v1/insight/operation/customer-churn/generate-signals`
- `GET /ai-api/v1/insight/operation/signals`

## 8. 风险与待确认

- 当前 CPT 的“90/180 天”口径是跨阈值当月新增名单，不是全量流失池。产品需求需要确认首页 KPI 展示哪一种，建议两种都支持但名称必须分开。
- `ds1` 是遗留一年未发货口径，当前 v2 页面主表未绑定，可暂不纳入第一版。
- `mara_group_desc` 与 `customer_name` 参数在 CPT 中存在条件绑定，但主 SQL 没直接使用参数过滤，过滤更可能发生在 FineReport 单元格层。平台实现时建议在后端查询层显式支持过滤，避免口径不可见。
- `差异化糖浆` 的人工原因和措施覆盖明显不足，第一版信号应把“资料缺口”作为经营风险，而不是直接把缺失解释成真实业务原因。
- 客户名称、年用量、销量和跟进措施属于内部经营敏感数据，阶段一仍按既有方案仅管理员可见。
