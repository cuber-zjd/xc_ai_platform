# 正文抓取与飞书正文同步修复

## 已确认原因

1. Firecrawl API 在运行，但 worker 于6月15日因 BullMQ Missing lock 异常退出，且没有自动重启策略。接口等待任务超时后，平台只能降级直接HTTP。
2. 头条多为 `sou.toutiao.com/search/jump` 搜索跳转，未规范为真实文章地址；页面也可能返回脚本外壳或安全验证，不能将这种页面误判正文。
3. 补抓原来串行执行，外层统一300秒超时，个别慢请求使已完成记录的统计一起丢失。
4. 飞书正文默认未选中，旧增量只比较同步时间，不会修复已同步但缺正文的记录。

## 本次范围

- 原安装恢复 worker，持久化重启策略；不升级镜像、不清空队列、不干预其他应用。
- 头条限定域名与文章路径解析，逐跳公开地址检查，保留原始链接与规范地址；403/429、验证码不密集重试。
- 固定补抓清单，跨进程锁，独立会话，抓取90秒、评审120秒分别限时；跨站并发3、同站串行及冷却，逐条审计。每日批次300秒只停止新派发，不撤销已完成结果。
- 正文抓到但评审失败记录为待评审；仍走原日期窗口、权限、去重和AI评审，不降低普通来源转正式门槛。
- 飞书默认同步正文，已同步记录按正文内容补写；同步后全表回读验证。
- 全量实测发现 `TooLargeCell`：正文最多180200字节，不能仅检查字符数。正文按 UTF-8 每段最多80000字节保存于“正文”“正文（续1）”等文本列，自动补列，不截断；回读按数字顺序拼接比较。正文缩短时清空旧续列，已有重复ID各行均更新。请求同时限制500行和约4MB，明确的超大单元格错误按二分定位单条，不阻断其他有效行；结果不明的网络异常不按此方式重放新增。
- 字节限制依据：[飞书官方日志同步说明](https://aily.feishu.cn/hc/1u7kleqg_pu4h2j7s)；该页字符/字节措辞并不完全一致，本实现采用较保守的80000字节并以真实全表回读验收。

## 验收口径

先运行本地回归，再使用唯一发布脚本部署后端和 Firecrawl 守护修复。生产运行 `insight_verify_fulltext_recovery.py --days 7 --repair --sync`，固定近七天缺正文清单，逐条归档成功、失败、待评审与延期。无论是否成功，都记录完整清单，不以少量样本代替整体。

该命令不生成报告，不发送消息。历史没有正文的记录不得用搜索摘要冒充正文；无法获取的站点需如实保留失败。

## 第二轮：持续探测与正文质量复核

### 改动及边界

- Firecrawl 增加独立端到端探测：`insight_check_firecrawl.py` 直接调用 Firecrawl，不允许 HTTP 降级掩盖故障；两个不同域名的已知文章使用随机查询参数，检查正文、预期标题标记和验证码。用户级 systemd timer 每15分钟运行，单站75秒、服务240秒上限，数据库 advisory lock 防重叠。
- 目标保存在服务器 `backend/.firecrawl-health.env`，权限0600、忽略Git；安装入口为统一部署脚本的 `-RepairFirecrawl`，只写原安装目录及对应用户单元。不修改其他项目容器。
- 首次失败记warning，连续三次失败记critical，恢复单独记录。告警写本机journal和管理员任务日志 `firecrawl_health`，失败进程非零退出。本轮没有对外告警消息；目标站点自身失效也可能导致报警，不能直接归因为worker崩溃。
- worker、API、浏览器和专属依赖使用Docker `unless-stopped`。退出可自动重启，人工停止不会强制恢复；进程仍活着但卡死不会被该策略重启，端到端探测负责发现，不自动强杀在途任务。现有worker真实取任务并发为3，未另外增加第二套容器重启守护。
- 无明确article容器的HTML增加trafilatura主体抽取，保留表格和链接、排除评论；确定性质量检查识别导航、重复、截断、标题匹配、资料页、视频简介、免责声明和交互控件残留。通过规则不代表人工事实核验或全文完整性认证。
- 精确UI行与完全重复长段落可清洗，原文和清洗候选留档。免责声明可能属于真实公告，不能仅凭关键词截断，无法确定时保留待核。AI正常入库链路发现质量问题时保留候选，不自动归为噪声。
- 历史复核只更新采集正文和质量元数据；关联正式情报只附质量标记，不覆盖人工正文，不改标题、日期、企业归属和权限，不触发资产模型、报告、飞书同步或消息。
